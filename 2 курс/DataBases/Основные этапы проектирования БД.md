1. Анализ требований: определить предметную область, бизнес правила (что она будет делать, как будет делать). Результат - это чётко сформулированное ТЗ.
2. Концептуальное проектирование: на этом этапе создаётся модель предметной области, которая отражает её суть без привязки к конкретной СУБД. 
	Ключевые задачи:
	- выделить сущности;
	- определить атрибуты
	- выявить связи между сущностями
	- сформулировать ограничение целостности.
	Результатом данного этапа будет ER-диаграмма.

![[Pasted image 20260917143852.png|667]]

3. Логическое проектирование: здесь концептуальная модель преобразовывается в форму понятной конкретной СУБД. 
	Ключевые задачи: 
	- перевод сущностей в таблицы атрибуты в заголовки столбцов, связи во внутренние и внешние ключи. 
	- Подбираются типы данных и обязательное или необязательное поле. 
	- Проводится нормализация (это процесс устранения избыточности и дублирования данных, чтобы повысить целостность и эффективность хранения). 
	Есть 4 формы нормализации: 
	- 1NF
	- 2NF
	- 3NF
	- BCNF
	Результатом данного этапа будет диаграмма с таблицами, типами данных и ключами.
![[Pasted image 20260917145311.png]]

4. Физическое проектирование: это самый технический этап, на котором логическая модель адаптируется под конкретную СУБД. 
	Ключевые задачи: 
	- Выбор СУБД с учётом требований проекта
	- Проектирование сущностей, атрибутов, первичных и вторичных ключей
	- Ввод тестовых данных
	- Проектирование физических ограничений
	- Реализация бизнес-правил (процедура, триггеры, запросы)
	- Настройка безопасности (определение прав доступа у пользователей)
	Результатом будет готовая база данных конкретной СУБД, в которую можно вносить реальные данные и использовать.
